# Release and demonstration checklist

## Before each release

- Current phase and actual course cutoff identified, using Australia/Sydney.
- Existing public/private status checked; public repo stays public.
- Current branch/remote/app identities confirmed; no unrelated repo touched.
- Appropriate checks for changed code and current course entrypoints green.
- Real required browser checks run, with a clear unverified list if blocked.
- Root README contains only current verified product promises; full /readme/ HTML.
- Root CLAUDE agrees with active phase, retaining course harness.
- PROCESS is current and evidenced, not filled with bracketed placeholders.
- Applicable reflection exists with truthful student writing; previous entries preserved.
- Final COMP8020 research-note exists as an actual cited argument, not a guide.
- Full history secret scan; no logging/response leaks. No tokens printed in reports.
- Database backup/migration compatible with old rooms, actual /data mount retained.
- Actual installed course preflight/ship used; tags/history not rewritten.
- Push/CI/deploy/live route status each observed, not inferred from local success.

First publication and production release are concrete actions. Use the release prompt only when intended; normal feature-branch sync is not initial publication. Passing a local check alone is not a submitted app. A past cutoff cannot be met retrospectively.

## C8 demonstration

Read approach → create/join → save one useful idea → refresh/return → find trace. Explain one real directing/grounding/correction choice and show its evidence. Current late changes remain later changes, not cutoff work.

## C9 demonstration

Two or more actual devices/browser identities. B joins, A sees without refresh; A adds, B sees; disconnect one, change other, reconnect to latest state. Present one behaviour ADR and defend it against the alternative. Voting can illustrate this if built; it is not required merely to satisfy C9 realtime.

## C10 demonstration

Classmates use product. Wen watches only live logs and narrates actors, actions, stage/outcome. No own UI clicking. Logging remains in the project. Terminal tail is enough; dashboard optional.

## Final walkthrough

Start at /readme/, invite two isolated sessions, supply required ideas, see live co-presence, open shortlist, vote/change, resolve rounds, reveal and return. Use a separate fixture for tie/partial-close cases. Test simultaneous operations, slow request and keyboard/resize. Explain limits: room invitation privacy, missing-vote closure, chance after persistent tie, single-machine storage and human judgement still needed.

## Session is separate

Attend and contribute to critique/riff; the pod's agent repo is not DayDraw. Read its own current code before writing its prompt.md. Preserve the difference between personal Final work and pod activity.
